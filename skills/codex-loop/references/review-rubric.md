# Codex 产出严审清单与打回模板

审核准绳以当前项目的工程规范与全局规则（如 `~/.gemini/config/GEMINI.md` 或 `~/.agents/AGENTS.md`）为基础，不重复其正文，聚焦审核动作与常见问题。

## 审核铁律

1. **只信代码与实测，不信口头总结**：先看真实改动（`git status` + `git diff`，排除派单前基线里的既有未提交改动）与验证输出，再对照 `handoff.json`。**禁止因功能跑通、无明显 Bug 或测试全绿就跳过必要性过筛**——每次严审必须专门核查新增防御、字段、拦截与请求是否真有必要存在，命中阻断项果断打回。
2. **保护合法边界，别误杀必要防御**：用户输入、第三方不可信数据、网络/IO/生命周期错误处理，以及有可达调用路径证明的真实边界，必须保留；不要为了极简删掉正确性或安全性保障。
3. **按影响分级，省着花返工配额**：对每条问题单独判断是否违反验收条件、现有契约或明确工程红线。只有阻断项触发返工；纯命名/格式偏好或轻量风格建议列为非阻断建议，不单独消耗 2 轮返工配额（若本轮已有阻断项，可顺带一并清理）。
4. **不确定的防御、拦截与业务边界先问用户，禁止全盘接受 Codex 理由**：先核对已有授权、现行需求与既有契约——能明确得出结论的直接按契约推进，无需反复请示；但代码里能查到技术隐患（如后端容错弱、历史脏数据、废弃字段残留），不等于业务上就应由当前改动去拦截或兜底。无论在 `implement` 严审、`review` 反向审查、`plan` 方案合并还是 `needs_input` 处理中，凡查证后仍**拿不准该留还是该删的防御逻辑、校验拦截、确认弹窗或业务边界取舍**，**严禁因 Codex 的技术理由听起来有道理就默认照单全收**——应将争议项、Codex 理由及保留/删除各自的真实代价精简列出，先问用户拍板，再决定放行、删改或打回。

## 红线一：过度防御（标 `[DELETE_OVERDEFENSE]`）

对照真实 Diff 与 `handoff.json` 中的 `guards_and_fallbacks`，前四类属于阻断项，命中即打回删除；第五类按影响定级；漏报或证据存疑核对契约后处理：

- **冗余二次校验（阻断）**：上游类型、请求封装、组件 prop 或已知调用方已保证契约，仍新增 `?.`、`?? []`、`typeof`、`Array.isArray`，或在契约已保证合法的不可编辑字段上反复做空值/合法性扫描。
- **静默吞错掩盖契约故障（阻断）**：用 `|| ''`、`?? []`、`catch { return [] }` 把本应暴露的接口或类型异常伪装成空结果/成功态。
- **无证据的假想加固（阻断）**：没有可达复现或并发场景证据，却新增锁、请求序号、队列、Promise 缓存、重试、防抖或旧版本兼容分支。
- **越界的功能级防御与死状态（阻断）**：在现有有效契约之外、未经用户明确要求，擅自新增历史废弃字段兼容、旧页面回读保护、由前端替后端兜底的字段范围/格式拦截、仅服务极小警告的额外预检网络请求或二次确认弹窗；以及在全仓及已声明对外协议中均无消费读点的**只写不读死字段、死状态列**（严审时必须核查新增字段/列的真实消费关系）。
- **过度包装与顺手大改（按影响分级）**：大面积顺手格式化、重排或重构与任务无关的代码标为阻断；仅用一次的小型 helper 或轻微风格包装作为非阻断建议，已有阻断项时顺带清理，或由主控收口时直接简化。
- **漏报与“自造单测”假证据（先查契约再决定）**：Diff 里新增防御/兜底/校验逻辑却未填入 `guards_and_fallbacks` 时，先核对调用方与契约——确有可达依据的补齐回执并保留，确认上游已保证的按冗余防御打回删除。`evidence` 只写空泛假设（如“以防接口返回异常”）或**仅写“单测/合成夹具已覆盖非法输入”均不算有效证据**——必须能指出真实上游契约、真实调用方或真实用户操作链，否则即使单测通过也按 `[DELETE_OVERDEFENSE]` 打回删除。

## 红线二：不粘锅与半成品（标 `[MUST_FIX]`）

- **假卡壳真甩锅**：代码里有线索可查、属于可逆小决策、或本可先把无阻塞部分做完却中途停下返回 `needs_input` / `needs_permission`（包括把项目内常规构建/测试误当报批项）→ 主控直接拍板或明确豁免，原会话打回做完。
- **只盖症状不修根因**：修 Bug 时仅在报错行补 `if (!x) return` 躲过去，未追查上游为何传入非法值 → 打回修根因。
- **改不全与同类漏改**：留下 `TODO`、注释掉旧代码不删、把死代码推给“后续处理”；或新增/修改/替换某项规则与能力时只改单点，未参照已有同类全仓补齐入口、配置、测试与说明，也未按旧说法反搜清掉过时描述 → 打回清理，且**只要发现一处同类漏改，打回时必须要求全仓复查同类一次补齐**。
- **推卸验证责任**：未跑必要构建/测试/类型检查就标 `done`，或命令失败时轻飘飘甩一句“可能是历史/环境问题”而不核实是否本次引入 → 打回实测，或由主控复核定性。
- **盲从走歪不吹哨**：任务前提或改法与仓库真实契约/架构明显冲突，却闷头按字面改完交差、既不喊停也不在 `design_concerns` 里给证据提醒 → 打回重评或上报用户校正方向。
- **免责腔污染最终回复**：Codex 在 `summary` 或 `design_concerns` 里写“理论上应该没问题，建议你再测一下”“注意以下假想风险”等无代码证据的免责套话时，主控交付给用户前必须剥离，只基于实测给出明确、担责的结论。

## 复发拦截与反向审查/方案过滤

- **复发问题机械化拦截（棘轮原则）**：普通小改动仍不强加单测；但被打回的是实测 Bug、契约违背或反复发生的同类漏改，且仓库已有类型检查、lint 或测试体系时，优先在同一次返工里补一条针对性类型约束或回归守卫测试（报错写清改法）。新增检查时已有违规记作欠账只减不增，新代码零违规；前端测试设施仍遵循共享工程规范。
- **反向审查与双盲方案过滤（防迁就 GPT 过度审查与扩边界入宪）**：接收 Codex 的只读审查或方案回执时，主控按「证据是否成立 → 修法是否扩界 → 当前任务是否授权实施」三步分流：
  1. **真实缺陷按任务授权处理**：有运行复现或静态代码证据（现行契约、真实调用方或可达操作顺序）证明的安全/鉴权漏洞、崩溃、算错丢数或既有契约回归——若当前任务已授权实施/修复，直接修，无需反复请示；若用户仅要求只读审查，只交付核验结论、位置与改法（不写项目文件）；若处于双盲方案阶段，纳入合并方案，按方案拍板后再实施。
  2. **假想风险直接滤**：既无运行复现，也无法从现行契约、真实调用方或可达操作顺序证明错误后果，或上游契约已保证的条目直接降级忽略，**不要为了迁就 Codex 在自己代码里加多余防御代码**（静态证据成立但当前只读环境未实跑的保留分级并注明未实跑条件）。
  3. **扩边界防御禁私自采纳或入宪**：若 Codex 提出的防御意见超出既有有效契约、会扩大需求范围、改变交互或引入长期包袱（如兼容历史废弃字段、保护旧页面回读、由前端替后端兜底范围/格式校验、新增阻断提示/二次确认弹窗或额外预检请求），**不得由主控直接采纳，更严禁直接写入 `AGENTS.md` 或设计文档固化为项目契约**；应单独说明现实代价与取舍交用户拍板，获明确同意后再落地。

## 打回指令格式

打回时发给 Codex 的内容必须逐条可执行，禁止模糊评价（如“写得太啰嗦请优化”）：

```markdown
审核未通过，请在本会话中按以下清单直接修复并重新验证，完成后仍按 JSON Schema 返回回执：

1. [DELETE_OVERDEFENSE] `src/foo.ts:42`
   - 问题：对 `fetchPage` 返回的 `page.rows` 加了 `(page?.rows ?? [])`，该封装已保证成功返回 `rows`，且未提供反例证据。
   - 改法：改为直接使用 `page.rows`。

2. [MUST_FIX] `src/bar.ts:88`
   - 问题：仅用 `if (!user) return` 跳过异常，未修复上游传入 `undefined` 的根因。
   - 改法：检查 `src/caller.ts:19` 并修复源头传参，同时跑通 `npm test`。

要求：仅修改上述条目及其直接连带项，不要重构无关代码（若上述条目命中同类漏改，须同步按 `<旧字段/旧规则>` 全仓复查共享同一契约的同类入口并一次改齐）；修改后实跑验证命令并如实填入 `verification`。
```
