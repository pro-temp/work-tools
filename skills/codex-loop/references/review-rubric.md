# Codex 产出严审清单与打回模板

审核准绳以当前项目的工程规范与全局规则（如 `~/.gemini/config/GEMINI.md` 或 `~/.agents/AGENTS.md`）为基础，不重复其正文，聚焦审核动作与常见问题。

## 审核铁律

1. **只信代码与实测，不信口头总结**：先看真实改动（`git status` + `git diff`，排除派单前基线里的既有未提交改动）与验证输出，再对照 `handoff.json`。
2. **保护合法边界，别误杀必要防御**：用户输入、第三方不可信数据、网络/IO/生命周期错误处理，以及有可达调用路径证明的真实边界，必须保留；不要为了极简删掉正确性或安全性保障。
3. **按影响分级，省着花返工配额**：对每条问题单独判断是否违反验收条件、现有契约或明确工程红线。只有阻断项触发返工；纯命名/格式偏好或轻量风格建议列为非阻断建议，不单独消耗 2 轮返工配额（若本轮已有阻断项，可顺带一并清理）。

## 红线一：过度防御（标 `[DELETE_OVERDEFENSE]`）

对照真实 Diff 与 `handoff.json` 中的 `guards_and_fallbacks`，前三类属于阻断项，命中即打回删除；第四类按影响定级；漏报先核对契约再定：

- **冗余二次校验（阻断）**：上游类型、请求封装、组件 prop 或已知调用方已保证契约，仍新增 `?.`、`?? []`、`typeof`、`Array.isArray`。
- **静默吞错掩盖契约故障（阻断）**：用 `|| ''`、`?? []`、`catch { return [] }` 把本应暴露的接口或类型异常伪装成空结果/成功态。
- **无证据的假想加固（阻断）**：没有可达复现或并发场景证据，却新增锁、请求序号、队列、Promise 缓存、重试、防抖或旧版本兼容分支。
- **过度包装与顺手大改（按影响分级）**：大面积顺手格式化、重排或重构与任务无关的代码标为阻断；仅用一次的小型 helper 或轻微风格包装作为非阻断建议，已有阻断项时顺带清理，或由主控收口时直接简化。
- **漏报或自报存疑（先查契约再决定）**：Diff 里新增防御/兜底逻辑却未填入 `guards_and_fallbacks` 时，先核对调用方与契约——确有可达依据的补齐回执并保留，确认上游已保证的才按冗余防御打回删除；`evidence` 只写空泛假设（如“以防接口返回异常”）的同样核实后处理。

## 红线二：不粘锅与半成品（标 `[MUST_FIX]`）

- **假卡壳真甩锅**：代码里有线索可查、属于可逆小决策、或本可先把无阻塞部分做完却中途停下返回 `needs_input` / `needs_permission`（包括把项目内常规构建/测试误当报批项）→ 主控直接拍板或明确豁免，原会话打回做完。
- **只盖症状不修根因**：修 Bug 时仅在报错行补 `if (!x) return` 躲过去，未追查上游为何传入非法值 → 打回修根因。
- **改不全与同类漏改**：留下 `TODO`、注释掉旧代码不删、把死代码推给“后续处理”；或新增/修改/替换某项规则与能力时只改单点，未参照已有同类全仓补齐入口、配置、测试与说明，也未按旧说法反搜清掉过时描述 → 打回清理，且**只要发现一处同类漏改，打回时必须要求全仓复查同类一次补齐**。
- **推卸验证责任**：未跑必要构建/测试/类型检查就标 `done`，或命令失败时轻飘飘甩一句“可能是历史/环境问题”而不核实是否本次引入 → 打回实测，或由主控复核定性。
- **盲从走歪不吹哨**：任务前提或改法与仓库真实契约/架构明显冲突，却闷头按字面改完交差、既不喊停也不在 `design_concerns` 里给证据提醒 → 打回重评或上报用户校正方向。
- **免责腔污染最终回复**：Codex 在 `summary` 或 `design_concerns` 里写“理论上应该没问题，建议你再测一下”“注意以下假想风险”等无代码证据的免责套话时，主控交付给用户前必须剥离，只基于实测给出明确、担责的结论。

## 复发拦截与反向审查过滤

- **复发问题机械化拦截（棘轮原则）**：普通小改动仍不强加单测；但被打回的是实测 Bug、契约违背或反复发生的同类漏改，且仓库已有类型检查、lint 或测试体系时，优先在同一次返工里补一条针对性类型约束或回归守卫测试（报错写清改法）。新增检查时已有违规记作欠账只减不增，新代码零违规；前端测试设施仍遵循共享工程规范。
- **反向审查过滤（防迁就 GPT 过度审查）**：接收 Codex 的只读审查回执时，主控逐条核对 `[BLOCKING]` 指向的 `文件:行号`、可达输入或操作顺序以及违背的契约是否真实成立；无法复现、上游契约已保证或靠多重假想拼凑的条目直接降级忽略，**不要为了迁就 Codex 在自己代码里加多余防御代码**。

## 打回指令格式

打回时发给 Codex 的内容必须逐条可执行，禁止模糊评价（如“写得太啰嗦请优化”）：

```markdown
审核未通过，请在本会话中按以下清单直接修复并重新验证，完成后仍按 JSON Schema 返回回执：

1. [DELETE_OVERDEFENSE] `src/foo.ts:42`
   - 问题：对 `fetchPage` 返回的 `page.rows` 加了 `(page?.rows ?? [])`，该封装已保证成功返回 `rows`，且未提供反例证据。
   - 改法：改为直接使用 `page.rows`。

2. [MUST_FIX] `src/bar.ts:88`
   - 问题：仅用 `if (!user) return` 跳过异常，未修复上游传入 `undefined` 的根因。
   - 改法：检查 `src/caller.ts:19` 并修复源头传参，同时跑通 `npm test`。

要求：仅修改上述条目及其直接连带项，不要重构无关代码；修改后实跑验证命令并如实填入 `verification`。
```
